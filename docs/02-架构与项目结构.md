## 0. 先修正我上一版的错误判断

在拿到真实代码之前，我写过一版"绿地架构"（React + 9 个 packages + SSE）。看过仓库后，那版**大部分不成立**，这里明确作废，避免后面对着一份错文档施工：

| 上一版判断 | 实际情况 | 修正 |
|---|---|---|
| 前端用 React | 是 **Vue 3.5 + Element Plus + AntV X6**，8 个页面已成型 | 保留 Vue，不重写。React 方案**作废** |
| 实时推送用 SSE | 已用 **Socket.IO**，且需要双向控制（pause/resume/stop/manual confirm） | 保留 Socket.IO。SSE 只适合单向，**作废** |
| 拆 9 个 packages 的 monorepo | 全仓 7.7k 行，1 人维护 | 只加 `packages/protocol`，其余不拆。9 包结构**作废** |
| 新建 Case 模型替代 Flow | Flow DSL 已被画布/引擎/报告/文档四方共用 | Flow 仍是唯一用例模型，**作废** |
| 白盒靠"更好的画布" | 白盒缺的是**运行时证据**，画布够用 | 改为 JaCoCo/V8 覆盖率取证（§6） |
| 绿地从零搭 | 黑盒链路已闭环并经真实项目验证 | 改为**分层 + 迁移**，不动骨架 |

> 保留下来的判断只有两条：**存储必须换 SQLite**、**安全必须在桌面化前补完**。这两条在真实数据（1737 条接口、每节点写盘）面前反而更硬。

## 1. 架构决策记录（ADR）

### ADR-1 · 存储：JSON 文件 → SQLite（WAL）

- **背景**：`store.js` 每次保存都 `readFileSync` + 全量 `JSON.stringify` + `writeFileSync`；`RunSession.persist()` 每个节点写一次，且把全部 events 一起写。
- **决策**：单文件 SQLite，`journal_mode=WAL`，执行明细按行插入。
- **驱动**：`better-sqlite3`（同步 API，与现有同步代码风格一致，写入微秒级）。
  - 备选 `node:sqlite`（Node 22 内置，免原生编译，利于桌面打包），但目前仍标记 experimental，且 API 子集不全 → **先 better-sqlite3，桌面打包阶段再评估切换**。
  - **版本钉在 `^12.11.1`（2026-11-09 实测修正）**：13.x 的 GitHub Release **不发布预编译产物**，装包必然触发源码编译（需要 Python + MSVC）；12.x 提供 node-v127 的 win32/linux 预编译包，`npm ci` 可直接落二进制。13.x 无 API 需求（本项目只用 `Database/pragma/prepare/transaction/backup`），**升级前必须先确认预编译包存在**。
- **影响**：`store.js` 保持同名导出（`listFlows/saveFlow/...`）作为门面，内部改实现，**上层路由零改动**。这是本次重构最重要的"低风险切口"。
- **迁移**：启动时检测 `data/*.json` 存在且库为空 → 一次性导入 → 重命名为 `*.json.bak`。

### ADR-2 · 执行引擎：保持单进程，加"会话持久化 + 受限并发"

- **背景**：`RunSession` 全内存，重启即丢；`runLoop` 串行。
- **决策**：
  1. 会话状态（当前节点、变量、已完成步骤）落 SQLite，`pause/resume/stop` 改为读库驱动，重启可恢复（FR-4.8）。
  2. 引入一个**进程内队列**（`p-queue` 级别的 50 行实现即可），并发度默认 3，按 `Suite.strategy.concurrency` 控制；每个 RunSession 变量域完全隔离。
  3. 不引入 Redis/BullMQ。单机产品，进程内队列足够；引入外部依赖会让桌面端打包变复杂。
- **影响**：`scheduler.js` 拆分——`RunSession` 保留调度语义，新增 `SessionStore` 负责持久化，`Runner` 负责队列。

### ADR-3 · 协议：新增 `packages/protocol`（唯一共享层）

- **背景**：Flow 类型只在 `frontend/src/types/flow.ts`；事件类型只在 `docs/EXECUTION.md` 的文字里；后端零类型校验。三方（前端 / 后端 / 未来 CLI）各写一遍。
- **决策**：新增一个**零依赖、纯类型 + 常量**的包：

```
packages/protocol/
├─ package.json          # "type":"module"，无 dependencies
├─ index.js              # 运行时导出：事件名常量、失败分类枚举、版本号
├─ index.d.ts            # Flow / Node / Edge / Execution / Coverage / 事件 payload
└─ validate.js           # 手写 schema 校验（不引入 zod，避免桌面端体积/依赖）
```

- **不做的**：不抽 `engine`/`store` 成独立包。后端仍然是一个可 `node src/index.js` 直接跑的应用，CLI 直接 `import` 后端模块（同仓同 runtime，没必要为复用付拆包成本）。

### ADR-4 · 白盒：外部 agent 取证，不做自研插桩

- **背景**：现有白盒 = 静态调用链 + 人工点"通过"。
- **决策**：按被测语言选取证方式，统一产出 `Coverage` 结构：

| 被测栈 | 取证方式 | 粒度 | 侵入性 |
|---|---|---|---|
| JVM（主场景） | JaCoCo agent，**每节点 reset/dump** | 行 | 需给 JVM 加 `-javaagent` |
| Node | `inspector` + `Profiler.takePreciseCoverage`（增量） | 行/函数 | 需 `--inspect` |
| 其他 | 导入 lcov / cobertura | 行 | 无（构建期产物） |
| 都没有 | `coverage: null` + UI 明示"无运行时证据" | — | — |

- **为什么不自研**：字节码插桩/源码映射是重活，JaCoCo 与 V8 已经是事实标准；我们的价值在**把覆盖证据按节点归因并展示**，不在采集器。
- **影响**：新增 `backend/src/coverage/`（详见 §6）。

### ADR-5 · 桌面端：Tauri 2 壳 + Node sidecar（SEA）

- **决策**：Tauri 2 做壳（体积小、系统 WebView），业务仍是**未改动的 Node 服务**，以 sidecar 形式随包分发；Web 端与桌面端加载同一套前端产物。
- **端口与握手**：sidecar 启动时监听 `127.0.0.1:0`（随机端口），把 `{port, token}` 打到 stdout 首行；Tauri 读取后注入 WebView。避免端口冲突和"裸奔 API"。
- **为什么不是 Electron**：体积与内存劣势明显；我们的 Node 逻辑本来就要单独跑，Tauri + sidecar 反而更干净。
- **代价**：需把 Node 打成单文件（SEA）或带 node 运行时；`better-sqlite3` 是原生模块 → 打包时按平台预编译，这是 M5 的主要风险点（见 §10）。

└───────────────┬──────────────────────────────────────────────┬────────────────────────────────────┘
                │ REST /api/*（Bearer token）                   │ WS（room=exec:<id>，seq 可重放）
┌───────────────▼──────────────────────────────────────────────▼────────────────────────────────────┐
│ backend（Express 4 + Socket.IO，唯一业务进程）                                                     │
│                                                                                                    │
│  routes/       ← 只做参数校验 + 调用 service，不含业务逻辑                                          │
│  services/     ← 用例编排（projects / flows / executions / suites / coverage / reports）             │
│  domain/       ← 纯逻辑：RunSession、validators、expression、matching、failure-classifier           │

┌──────▼─────────┐  ┌────────▼─────────┐  ┌─────────────▼──────────┐  ┌────────▼──────────────────┐
│ Apifox MCP     │  │ 被测服务          │  │ 本机前端工程目录        │  │ JaCoCo agent(被测JVM)     │
│ apifox-mcp-    │  │（dev/test/prod）  │  │（增量扫描/符号索引）     │  │ V8 inspector(Node服务)    │
│ server(npx)    │  └──────────────────┘  └────────────────────────┘  │ lcov 文件                 │
└────────────────┘                                                     └───────────────────────────┘
                          ┌──────────────────────────────┐

                          └──────────────────────────────┘

**三条不变式**

1. **一个业务进程**：后端既是 API 也是执行器。桌面端只是换了个壳，不是第二套实现。
2. **依赖单向**：`routes → services → domain → infra`。`domain` 不 import express/socket/fs；`infra` 不 import services。
3. **协议先行**：任何跨进程/跨模块的数据结构，先改 `packages/protocol`，再改实现。

## 4. 后端分层与依赖规则

### 4.1 层职责

| 层 | 可以做 | 禁止 |
|---|---|---|
| `routes` | 读参数、调 service、映射 HTTP 状态码 | 直接访问 `store`/`fs`/`axios` |
| `services` | 编排多个 domain/infra、事务边界、发事件 | 写 HTTP 响应；引 `express` |
| `domain` | 纯计算：调度、断言、表达式、匹配、归类 | `fs`/`net`/`express`/`socket.io`（通过注入的端口调用） |
| `infra` | SQLite、MCP、扫描、覆盖率采集、导出、密钥 | 反向依赖 services |

### 4.2 端口（Port）注入

`RunSession` 现在直接 `import { store }`，改分层后必须解耦，否则没法单测：

```js
// domain/engine/run-session.js
export class RunSession {
  constructor({ flow, vars, ports }) {
    this.http = ports.http        // { request(node) }
    this.recorder = ports.recorder // { stepStart, stepEnd, finish, emit }
    this.coverage = ports.coverage // { reset(), dump(nodeId) } | null
    this.clock = ports.clock
  }
}
```

生产实现放 `services/executions/ports.js`，测试实现是内存 fake —— **这是"引擎可单测"的唯一前提**（D5）。

### 4.3 强制约束（用 lint 守住，不靠自觉）

**已启用（M1-5）**：`@eslint/js` + `typescript-eslint` + `eslint-plugin-vue` 的推荐集，
`--max-warnings=0` 作为门禁；只挡逻辑类问题（未定义变量、重复键、不可达代码、Vue 模板误用），不引入风格规则。

**目标态（随拆分逐步加）**：

- `domain/**` 不得出现 `express|socket.io|node:fs|axios`。
- `routes/**` 不得出现 `store|fs\.|axios`。
- 循环依赖一律 CI 失败（`madge --circular`）。

## 5. 事件契约 v2

现有事件能驱动动画，但**不能重放、不能去重、不能断线续传**。

### 5.1 信封（所有事件统一）

```jsonc
{
  "v": 2,
  "executionId": "uuid",
  "seq": 17,             // 单次执行内严格自增，从 1 开始，用于去重与补洞
  "ts": 1762500000000,
  "type": "step_end",
  "payload": { }
}
```

> **落地口径（M2-5）**：`type` 沿用 `docs/EXECUTION.md` §3 的既有事件名（`flow_start` / `step_start` /
> `step_end` / `manual_wait` / `flow_end` …），不在此刻改名；v2 新增的是 `v` 与 `seq` 两个信封字段。
> `seq` 由 `RunSession.emit()` 同步分配，**WS 推送与落库使用同一个号**，避免前端去重时丢事件。

### 5.2 事件表

| type | 关键 payload | 前端用途 |
|---|---|---|
| `run.start` | `flowId, flowName, envId, totalNodes, startedAt` | 初始化画布 |
| `run.status` | `status: running\|paused\|passed\|failed\|stopped` | 顶部状态条 |
| `node.enter` | `nodeId` | 节点发光 |
| `step.start` | `nodeId, attempt, requestPreview` | 请求卡片 |
| `step.end` | `nodeId, statusCode, durationMs, checkSummary, failureClass?, failureReason?, coverageId?` | 节点变色 + 归类徽标 + 覆盖率徽标 |
| `check.result` | `nodeId, check{expected,actual,message,pass}` | 断言逐条打勾 |
| `coverage.dump` ★ | `nodeId, coverageId, source, mode, status, bytes, error, pending` | 覆盖率面板增量刷新；M3-1 只报告「取证完成」，`covered/total` 由 M3-2 解析后补 |
| `coverage.analyzed` ★ | `executionId, analyzed, failed, skipped, total, durationMs, coverage[{coverageId,nodeId,status,covered,missed,total,lineRate,files,classes,error}]` | M3-2 分析结束后的**单条汇总**事件（不带完整 `files[]`）；前端收到后重拉 `/coverage`，避免大事件挤占 WS |
| `log` | `level, nodeId?, message` | 控制台 |
| `manual.wait` | `nodeId, prompt` | 弹人工确认 |
| `run.end` | `summary{passed,failed,skipped,durationMs,matchedAll}` | 汇总卡片 |

### 5.3 断线重放

- 事件全部落 `execution_events` 表（`execution_id, seq, ts, type, payload_json`），主键 `(execution_id, seq)`。
- `seq` 由 `RunSession` 在 `emit()` 时同步分配；`executions.event_seq` 是跨进程持久化游标，新建会话从库里续上，
  进程重启后不会从 1 重号。攒批提交（20 条 / 200 ms）不改变号段，`appendExecutionEvents()` 优先采用 `evt.seq`。
- `GET /api/executions/:id/events?after=<lastSeq>&limit=<n>` 返回 `{ id, lastSeq, events[] }`；
  `after` 是排他游标，`limit` 只截断本页、不影响 `lastSeq`；记录不存在返回 404 `EXECUTION_NOT_FOUND`。
  非法 `after` / `limit` 按 0 / 默认值处理，不抛错（前端枚举版本落后时不应炸列表）。
- 前端订阅顺序：**先 `join` 房间，再按 `lastSeq` 调 `backfill()` 补齐**；回放期间到达的实时事件先缓冲，
  回放落地后按 `seq` 排序合并、`seq <= lastSeq` 丢弃（幂等）。顺序反过来会在「回放完成 → join 成功」
  之间丢事件（现场故障：`manual_wait` 掉进这条缝，画布永久停在「执行中」），详见 §5.3.2。
- `flow_resume` 是恢复专用事件：重启后只补这一条，**不重放 `flow_start`**；前端据此把画布切到「续跑」状态。
- **为什么不用 SSE**：我们需要客户端 → 服务端指令（pause/resume/stop/confirm），SSE 做不到；Socket.IO 已具备。

#### 5.3.2 前端执行态一致性（M2-5 补强）

执行页要回答用户两个问题：「现在还在跑吗？」「总共跑了多久？」。为此定了三条不变式：

| 不变式 | 落地方式 | 回归手段 |
| --- | --- | --- |
| 耗时以**服务端**为准 | `flow_start` / `flow_resume` 事件带 `startedAt`（毫秒），前端 500 ms 心跳算差值；结束后改用 `summary.durationMs` 定格 | 执行深场景 **A9b**（`startedAt` 为整数且等于详情 `startedAt`） |
| 事件不丢帧 | `EventSync`：join → beginReplay → 回放 → endReplay（合并缓冲、按 seq 去重）；4 s 定时对账 `backfill()` 兜底 | `frontend/test/event-sync.test.mjs` 5 例（含本次故障复现） |
| 等待人工确认不能像卡死 | `manual_wait` 驱动状态条橙色徽标 + 顶部横幅 + 自动选中该节点；`执行中/已暂停/等待人工确认/已通过/未通过/已停止` 六态 | 浏览器实测（见 §11 M3-1 验收） |

- **为什么计时不能用本地 `Date.now()` 兜底当准**：刷新/重连后本地起点会归零，用户看到的「已执行」与
  `summary.durationMs` 对不上。现在连接时用本地时间只是占位，`flow_start` / `flow_resume` 一到就被服务端值覆盖。
- **刷新或重新进入画布**：`GET /api/executions?flowId=` 找 `running` / `paused` 的会话自动接上（含全量回放），
  不要求用户「重跑一次」才能看到正在跑的执行。
- **对账兜底的必要性**：Socket.IO 重连丢帧、代理断流、进程重启都可能让前端游标落后；4 s 一次
  `after=lastSeq` 增量查询在 `lastSeq` 已追上时只返回空数组，成本可忽略，但能保证界面最终一致。


#### 5.3.1 会话恢复（M2-5）

恢复点固定在**节点边界**，`executions.resume_json` 每次覆盖写入：

```jsonc
{
  "eventSeq": 17,           // 事件游标，恢复后从 18 继续
  "stepSeq": 5,             // 步骤行号，避免覆盖历史步骤
  "executed": ["n1","n2"],  // 进入过执行的节点（含人工等待中）
  "done": ["n1"],           // 已出结论的节点（passed/failed/条件 skipped）
  "ready": ["n2"],          // 下一轮待执行队列
  "vars": { },              // 已掩码的变量快照（S7）
  "paused": false,
  "savedAt": 1762500000000
}
```

- **HTTP 节点原子**：节点执行完才更新恢复点；崩溃时正在进行的尝试补成 `skipped`（`error` 含「服务重启」），
  该节点重新执行，不会出现「步骤已 passed 但变量没落库」。
- **`executed` ≠ `done`**：`executed` 用于「末尾未执行节点补 skipped」，`done` 用于恢复时过滤待执行队列与
  计算前沿；人工等待中的节点在 `executed` 里但不在 `done` 里，重启后会重新等待确认，而不是被跳过。
- 已完成节点不重跑：`resume.ready` 先剔除 `done`，缺失快照时用 `frontier()`（未完成且入口/前驱已完成的节点）兜底。
- **暂停跨重启**：`paused` 随快照落库；重启后保持 `paused`，不擅自继续，等用户 `resume`。
- **secret 不落快照**：`vars` 写入前统一掩码；恢复时仅把「值为环境 secret 且快照为 `***`」的键用本次重新解密
  的环境值补回。`extract` 恰好取到 secret 明文的变量仍保持 `***`（S7 取舍，见 §8）。
- **套件不自动续跑**：未完成的 `suite_runs` 收敛为 `stopped`，`summary.message` 写明「服务重启」；
  其子执行按普通会话恢复，历史报告与重试记录不丢。

## 6. 白盒运行时证据设计（核心）

### 6.1 目标

> 对每个节点，回答三个问题：
> 1. 这次请求触发了哪些**源码行**？
> 2. 这些行**属于哪个类/方法**？
> 3. 我期望它命中的方法，**命中了吗**？

### 6.2 JaCoCo 方案（JVM，主场景）

**采集链路（2026-11-09 PoC 实测通过，见 `03-白盒PoC方案.md`）**

```
被测 JVM: -javaagent:jacocoagent.jar=output=tcpserver,port=6300,address=127.0.0.1
                │
                │  连接后 agent 先发 5 字节 exec 头：01 C0 C0 10 07
                │  客户端必须回写同样 5 字节，之后才进入命令/响应
                ▼
backend/src/coverage/jacoco-client.js     （M3-1 · 纯协议层：只管把字节拿回来）
   reset()        → 40 00 01   （节点开始前）
   dump()         → 40 01 00   （节点结束后，返回 exec 数据块，以 0x20 结尾）
   dumpAndReset() → 40 01 01   （M3-1 采用：取数 + 清零原子完成，无窗口期）
                │
                ▼
backend/src/coverage/collector.js         （M3-1 · 会话级连接复用 + 熔断 + 降级落库）
                │
                ▼
SQLite coverage.exec_blob（单节点实测 118~158 B，空载 36 B）
                │
                │  执行结束后一次 JVM 批量分析（jacococli 实测约 200 ms/节点）→ M3-2
                ▼
jacococli.jar report  →  XML  →  解析成 Coverage（写 coverage.result_json）
```

**远程控制协议（反编译 agent 0.8.12 确认；网传"4 字节魔数 `40 C0 10 00`"是错的）**

| 方向 | 字节 | 含义 |
|---|---|---|
| agent → client | `01 C0 C0 10 07` | exec 头（magic `0xC0C0` + 格式版本 `0x1007`），连接建立即发送 |
| client → agent | `01 C0 C0 10 07` | 必须回写；agent 的 reader 要求首块是 header，否则直接断连 |
| client → agent | `40 <dump> <reset>` | 唯一命令帧，共 3 字节 |
| agent → client | `10` + UTF id + int64×2 | SESSIONINFO |
| agent → client | `11` + int64 classId + UTF 类名 + varint 探针数 + 位图 | EXECUTIONDATA（位图 LSB-first） |
| agent → client | `20` | CMDOK，本次响应结束 |

**关键设计点**

| 点 | 决策 | 理由 |
|---|---|---|
| 传输 | TCP 直连 agent，**不用 JMX** | 协议只有 1 个命令帧（2 个布尔开关），`net.Socket` 即可；JMX 从 Node 侧很笨重 |
| 节点隔离 | 节点前 `reset`、节点后 `dump` | 实测证明 reset 可靠（A∩B=∅）；否则只有全局覆盖率 |
| 取数方式 | 优先 `dumpAndReset`（`40 01 01`） | 省一次往返，且消除"dump 完成到 reset 完成"之间的漏计窗口 |
| 分析时机 | 执行结束批量分析 | jacococli 实测 192~217 ms/节点，逐节点起 JVM 在 12 节点时是秒级叠加 |
| 归因 | exec 快照 + 类文件 → 行级 `covered/missed` | 类文件路径从被测项目 `target/classes` 或 jar 里取 |
| 降级 | 配置了但连不上 → 写 `status='unavailable'` 行（带稳定错误码）；未配置 → 不产行 | 绝不能把"没证据"显示成"0% 覆盖率"或"通过"（FR-3.2.7 / AC-3.2.7） |

> **M3-1 落地口径（2026-11-10）**
>
> | 项 | 内容 |
> |---|---|
> | 配置 | 环境 `settings.coverage = {source, host, port, timeoutMs, enabled}`；`source` 只接受 `jacoco`（其余 400 `ENV_BAD_COVERAGE`），缺省 `host=127.0.0.1` / `port=6300` / `timeoutMs=5000` / `enabled=true` |
> | 采集点 | HTTP 节点：`begin`（reset）→ 请求 + 断言 → `finally`（`dumpAndReset`）；**节点结论先于取证**，取证抛错只落 `unavailable`，绝不改写节点结论 |
> | 连接 | 一次执行复用一条 TCP 连接；会话内首次连接失败即熔断，后续节点直接写 `unavailable`，不逐节点重试拖长执行 |
> | 存储 | `007_coverage.sql`（`user_version=7`）建 `coverage`：每节点一行 `status='captured'` + `exec_blob`；`result_json` 留给 M3-2；`(execution_id,node_id)` 唯一，重跑是新执行不覆盖历史 |
> | API | `GET /api/executions/:id/coverage` → `{executionId,count,pending,unavailable,coverage[]}`，**投影不含 `execBlob`**；未知执行 404 `EXECUTION_NOT_FOUND` |
> | 事件 | 每次取证追加一条 `coverage.dump`：`{nodeId,coverageId,source,mode,status,bytes,error,pending}`，与 `step.end.coverageId` 一一对应 |
> | 验证 | 单测 13（协议）+ 8（采集器）+ 2（调度集成）；场景 12 的 12.1~12.8；`npm run verify:jacoco` 真实 agent **6/6**（`.exec` → jacococli XML，A/B 命中不串） |

> **M3-2 落地口径（2026-11-10）**
>
> | 项 | 内容 |
> |---|---|
> | 分析时机 | `finish()` 先写 `flow_end` / 汇总 / 落库，再异步执行 `analyzeCoverage()`；**分析不阻塞执行结论**，失败只 `log`，不改执行状态 |
> | 输入 | 只取本次执行 `status='captured'` 的 JaCoCo 快照；每节点把 `exec_blob` 写临时 `.exec`，单独跑一次 `jacococli report`（per-node 归因，不做差集） |
> | 命令 | `java -jar jacococli.jar report <node>.exec --classfiles <dir> [--sourcefiles <dir>] --xml <node>.xml`；`classfiles` 来自 `settings.coverage.classfiles`，CLI/Java 可被 `cliPath` / `javaBin` / `JACOCO_CLI` / `JAVA_BIN` 覆盖 |
> | 解析 | `coverage/jacoco-report.js` 纯函数：`files[]`（`covered`/`missed` 行号数组）、`classes[]`（LINE 计数 + `methods[]`）、`totals{files,classes,covered,missed,total,lineRate}`；行命中按 `ci > 0`，类级 counter 先剥离 `<method>` 块 |
> | 写回 | `coverage.result_json` + `status='analyzed'` + `analyzed_at`；**`exec_blob` 永不改写**，解析规则升级可重算 |
> | 降级 | 未配置 `classfiles` → 不分析，行保持 `captured` + `pending=true`；配置了但 CLI/类目录缺失或 jacococli 非零退出 → 行仍 `captured`（证据保留）+ 稳定 `error`，投影计 `analysisFailed`，不混进 `pending` |
> | 错误码 | `COVERAGE_CLASSFILES_MISSING` / `COVERAGE_CLI_MISSING` / `COVERAGE_JAVA_MISSING` / `COVERAGE_ANALYZE_FAILED`（消息统一 `<code>: <detail>`） |
> | API | `GET /api/executions/:id/coverage` 增 `analyzed` / `analysisFailed`；`pending` 只算 `captured && !error` |
> | 事件 | 成功/部分失败后补发一条 `coverage.analyzed`（`reason=NO_PENDING_EVIDENCE` / `CLASSFILES_NOT_CONFIGURED` 不发，保持「未分析」可辨） |
> | 验证 | 单测 `jacoco-report` 5 + `coverage-analyzer` 6 + 调度异步分析 1；场景 12.9（类目录缺失 → `analysisFailed=2`、证据保留）与 12.10（未配置 → 永久 `pending`）；`npm run verify:jacoco` **9/9** 真 JVM 闭环 |

**per-node 归因：不需要差集（PoC 修正了原设计）**

原设计假设 exec 探针是累计的，需要 `probe(K) AND NOT probe(K-1)`。实测结果：**reset 后探针确实清零**，每节点快照互相独立。

```
reset() → 节点请求 → dump() = 只含本节点命中的 exec
```

H2 证据：node-A 命中订单 10 行；node-B 命中订单 0 行、库存 9 行；`A∩B=∅`。因此 M3-2 直接"每节点 exec → jacococli"即可，**省掉差值实现（约 1 d）**。

差集逻辑只作为 fallback 保留（agent 不支持 reset，或 dump 失败需重试）。注意两个真实场景的语义：

- **共享工具类**被多个节点调用时，同一行会出现在多个节点里——这是正确行为，UI 上区分"本节点独占"与"共享命中"；
- **异步任务**在 dump 之后才执行的行不会被计入本节点——需要 UI 提示"覆盖率仅覆盖同步链路"。

**PoC 实测基线（7 个类的 fixture，2026-11-09）**

| 指标 | 实测 | 用途 |
|---|---|---|
| exec 体积（空载 / 单节点） | 36 B / 118~158 B | 决定存 SQLite BLOB，不落文件 |
| reset + dump 往返 | 0~1 ms | 每节点取证开销可忽略 |
| jacococli 单节点分析 | 192~217 ms | 12 节点约 2.4 s，批量分析成立 |
| 3 节点全链路（请求 + 取证 + 分析 + 断言） | < 3 s | 满足"点执行到出结论"的体验 |

### 6.5 统一数据结构

```jsonc
{
  "id": "cov_uuid",
  "runId": "...", "nodeId": "...",
  "source": "jacoco",              // jacoco | v8 | lcov
  "mode": "per-node",              // per-node | snapshot
  "status": "analyzed",            // captured（已取证待分析/分析失败）| analyzed | unavailable
  "error": null,                   // 稳定 code：COVERAGE_ANALYZE_FAILED / COVERAGE_CLASSFILES_MISSING / ...
  "capturedAt": 1762500000000,
  "analyzedAt": 1762500001234,
  "files": [
    { "path": "com/demo/order/OrderService.java",
      "covered": [42,43,44,47], "missed": [50,51,55], "total": 7 }
  ],
  "classes": [
    { "name": "com.demo.order.OrderService", "source": "com/demo/order/OrderService.java",
      "covered": 42, "missed": 16, "total": 58,
      "methods": [ { "name": "create", "desc": "()V", "line": 40, "covered": 6, "missed": 2, "total": 8 } ] }
  ],
  "totals": { "files": 1, "classes": 1, "covered": 42, "missed": 16, "total": 58, "lineRate": 72.41 }
}
```

> **M3-2 口径**：`files[]` 给行号数组（UI 标未覆盖行、跳源码）；`classes[]` / `methods[]` 给 LINE 计数（白盒断言 M3-4 用）；`totals` 是全量汇总，面板直接显示 `covered/total` 与 `lineRate`。`status` 与 `error` 是**证据状态**，不能由 `covered=0` 反推：没采到是 `unavailable`，采到未分析是 `captured+pending`，分析失败是 `captured+error`。

### 7.1 表结构（目标 13 张；M1 / M2-1 / M2-2 / M2-3 / M2-5 / M3-1 / M3-2 已落地 12 张）

> `003_environments.sql` 建 `environments` / `environment_secrets`，并给 `executions` 加

> `suite_run_id`；`005_failure_class.sql` **不建表**，只给 `executions` 加
> `failure_class` / `failure_reason` 两个投影列 + 索引；`006_session_resume.sql` **不建表**，
> 只给 `executions` 加 `resume_json`（节点边界的恢复快照）；`007_coverage.sql` 建 `coverage`
> （每节点一份白盒原始快照），合计 **12 张**。**M3-2 不新增表/列**：只把 `result_json` /
> `analyzed_at` / `status=analyzed` 写入 `coverage`，原始 `exec_blob` 保持不变。
> 其余表随各自 issue 增量迁移，用 SQLite `user_version` 串版本号。
> 本阶段刻意保留"整对象 JSON 列"（`graph_json` / `data_json` / `detail_json`），换取
> **零丢失**与**可回退**；`endpoints` 留在 M1-x，`coverage` 已由 M3-1/M3-2 落地（见 §6.2、下方 DDL）。

**实际 DDL 与下图目标模型的差异（已落地部分以此表为准）**

| 目标模型 | 实际实现 | 原因 |
|---|---|---|
| `execution_steps` 拆 `request_json`/`response_json`/`expected_json`/`actual_json`/`duration_ms`… | `data_json` 存完整 step，另设 `node_id` / `status` 两个投影列 | step 只被"整对象读取"，按字段拆列会让 M2 每次加字段都要改表；投影列只服务筛选与统计 |
| `step_checks(step_id, idx, check_json)` | 未拆，checks 仍在 `data_json` 内 | 单条 step 的 checks 只随 step 一起读，拆表只会多一次 join；等出现"按断言聚合统计"的需求再拆 |
| `executions.variables_json` | `context_json`（`{nodes, edges, vars, environment}`） | 详情页一次要 nodes/edges/vars/环境快照，合并成一次写；每次执行只在开始/结束/停止各写一次 |
| `executions` 无事件游标 | `event_seq` | 事件 `seq` 的单一分配源，批量提交时在事务内读-增-写，保证执行内严格自增 |
| `executions` 无恢复快照 | `resume_json` | 节点边界覆盖写入 `{eventSeq,stepSeq,executed,done,ready,vars,paused,savedAt}`；vars 已掩码（S7），重启时只补回环境 secret，不落明文 |
| — | 保留 `detail_json` | M1-1 的历史明细原样留档，回填后仍可回退；磁盘代价约 +216 KB |
| `environments` 只有基础列 | 一次建足 `headers_json` / `settings_json` / `version` / `updated_at` | 全局请求头是 M2-1 需求；`settings_json` 预留 M3 覆盖率采样，避免再 ALTER；`version` 给执行记录做对齐 |
| `secrets(id, env_id, key, value_enc)` | `environment_secrets(environment_id, key, value_blob)` 复合主键 | 密钥天然按「环境 + 键名」唯一；AAD 绑定 `envId|key`，密文被搬到别的环境/键名下会解密失败 |
| `suite_runs` 只有 `suite_id/status/summary_json` | 另存 `suite_name` / `project_id` / `strategy_json` / `env_id` / `env_version` | 执行开始时快照套件名、策略与环境版本；之后改名/改策略/删环境都不影响历史报告 |

### 7.2 为什么 Flow 不拆表

画布永远是"整图读写"，拆成 `flow_nodes`/`flow_edges` 只会让保存从 1 次写变 N 次写，并在事务里制造一致性问题。**Flow 是不可分割的聚合根**，用 `graph_json` + `version` 乐观锁即可。

### 7.3 写入策略

- **M1-2 已生效**：执行中 `execution_steps` 按 `(execution_id, seq)` **UPSERT**——节点开始写一次 `running`，
  结束时覆盖同一行，不做"整份 detail 重写"，也不随已完成步骤数增长；事件按 `(execution_id, seq)` 主键
  批量插入，攒 **20 条或 200 ms**（`setTimeout(...).unref()`，不阻止进程退出）提交一次。
- `executions.context_json`（nodes/edges/vars）只在开始、结束、停止各写一次；`event_seq` 是事件序号
  的单一分配源，`appendExecutionEvents()` 在事务内读-增-写，空批次直接返回 0。
- 执行结束时先落 `summary_json` 并回写 `vars`（含响应提取的变量），再发 `flow_end`；`finish()` 的最后
  一次 `persist()` 把剩余事件全部刷盘，保证库里事件数与内存一致。
- **M2-5 已生效**：每个节点边界（开始/结束/暂停/停止/人工等待）覆盖写 `executions.resume_json`；
  恢复时按 `done` 过滤 `ready`，缺快照时退回 `frontier()`。进行中的尝试补 `skipped`（原因含「服务重启」），
  不重跑已完成节点；未完成的套件运行收敛为 `stopped`（不自动续跑）。
- 回填历史：`infra/store/backfill.js` 的 `backfillExecutionRows()` 把 M1-1 的 `detail_json` 展开成
  `context + 行`，由 `openDatabase()`（老库升级）与 `migrateLegacyJson()`（首次导入）共用；判据是
  `detail_json IS NOT NULL AND context_json IS NULL`，事务内完成，重复调用零开销。
- 保留策略：`executions` 默认保留 90 天/最近 500 次，超出的仅保留 summary（可配置）。
- **M1-1 已生效**：项目保存只 `UPSERT` 自己那一行，不再重写 3.4 MB 的 `projects.json`；列表读投影列（`interface_count` / `folders_json` / `scan_summary_json`），不碰 `data_json`。

| 数据 | 单条大小 | 500 次执行 | 结论 |

## 9. 报告、导出与趋势

### 9.1 失败归类（规则，非猜测）

唯一事实源：`backend/src/reporting/classify.js`。纯函数、无 IO、不接 ML：每条结论都能指回
「哪个步骤、哪条证据、哪条规则」，测试人员可以在报告里看懂并反驳。

**8 类与判定依据（按代码顺序，先命中先出）**

| FailureClass | 中文 | 判定依据 | 典型 failureReason |
|---|---|---|---|
| `dependency` | 前置依赖 | `step.status === 'skipped'`：前置节点失败或分支条件未命中，本节点根本没跑 | `前置节点失败或分支条件未命中，本步骤未执行` |
| `manual_reject` | 人工驳回 | `actual.manual === true && actual.confirmed === false`，或首个未通过的 check 是 `type: 'manual'` | 测试人员备注原文 |
| `timeout` | 超时 | 错误文本命中 `ECONNABORTED/ETIMEDOUT/timeout of Nms/request timed out`；或 `duration` check 超上限 | `请求失败：timeout of 30ms exceeded（GET …）` |
| `network` | 网络不可达 | 错误文本命中 `ECONNREFUSED/ENOTFOUND/ECONNRESET/EAI_AGAIN/ENETUNREACH/EHOSTUNREACH/EPROTO/EPIPE/getaddrinfo/socket hang up/CERT_*/ERR_TLS` | `请求失败：connect ECONNREFUSED 127.0.0.1:6773（GET …）` |
| `script` | 脚本/配置 | 请求层异常但不属超时/网络（含「变量未解析」「节点未配置请求地址」「不支持的节点执行类型」）；或失败但无任何证据的兜底 | `变量未解析：http://…/{{ghostPath}}` |
| `status` | 状态码不符 | 首个未通过 check `type: 'status'` | `期望 等于 500，实际 200` |
| `schema` | 结构不符 | 首个未通过 check `type: 'schema' / 'json_schema' / 'body_schema'` | `期望 存在 ["$.data.token","$.data.role"]，实际 "缺失 $.data.role"` |
| `assertion` | 断言不符 | 其余未通过 check（`json_path` / `body_contains` / 表达式等） | `期望 等于 99，实际 1` |

**三条优先级口径（都是踩过坑之后定死的）**

1. **超时先于网络**：Node 的连接超时也带 `CONN` 字样（`ECONNABORTED`），只按关键字表顺序判会把
   「响应太慢」误报成「连不上」，所以 `TIMEOUT_RE` 一定先跑。
2. **人工驳回先于断言与错误文本**：人工不通过时也会写一条 `manual` check，若不优先，会被
   兜底的 `assertion` 吞掉，缺陷就归错责任人。
3. **无 check 证据的 error 归 `script`**：请求根本没发出去（变量未解析、URL 未配置、节点类型
   不支持）是流程自己的问题，不能算到被测接口头上。`executor` 因此在替换后仍含 `{{var}}`
   的 URL 直接抛错并**不发请求**（`step.request` 为 null，报告里能看出「未发起请求」）。

**结构断言（M2-3 新增 check 类型）**

`expected.checks` 支持 `{ "type": "schema", "value": ["$.data.token", "$.data.role"] }`：
`value` 给必填路径数组（也可给单个字符串），口径与 `op: 'exists'` 一致 —— 取不到（`undefined`）
**或**为 `null` 都算结构缺失；没配任何路径属于流程写错，直接不通过并提示「未配置必填字段路径」。
失败 check 的 `type` 就是 `schema`，因此归类天然落在 `schema`，不需要额外文本匹配。

**归类的两个时机**

| 时机 | 位置 | 语义 |
|---|---|---|
| 写入时 | `scheduler.saveStep()` / `finish()` | 每步结束即分类，`failureClass/failureReason` 随 step JSON 落 `execution_steps.data_json`；执行级写 `executions.failure_class/failure_reason` 投影列，并把 8 类计数写进 `summary.failureClasses` |
| 读取时 | `enrichExecutionDetail()`（详情接口 + `?failureClass=` 筛选） | 老数据没有归类字段 → 现算补齐，**幂等且不回写**；步骤级、执行级投影列、8 类计数分别判空补 |

读取时补齐是**兼容层而非第二事实源**：新数据永远走写入时结果，同一份老记录多次读取结果一致，
删库重放也不会漂移；M2-4 导出直接复用同一函数，保证「界面看到 = 导出拿到」。

**口径一致性（场景 9.10 锁死）**：`step_end` 事件 payload、`detail.steps[i]`、
`detail.summary.failureClass/failureReason/failureClasses`、`GET /api/executions` 行、
套件 `summary.flows[i].failureClass`（含 `attemptExecutions`）五处必须完全相同。

**与 secret 的关系（S8 的前置）**：归类永远基于 `this.mask(step)` 之后的数据。`executor` 会把
URL 拼进异常文案（`请求失败：…（GET http://host?token=<明文>）`），若先归类后掩码，
密钥就会以「失败原因」的形式泄漏到列表、事件和导出。因此写入前统一
`classifyStep(mask(step))`，再对 `failureReason` 二次 `mask()`。

**边界**：`skipped` 在**步骤级**始终标 `dependency`（报告要能看出它没跑、为什么没跑）；
但在 `passed` / `stopped` 的执行里，**执行级**汇总不把这类跳过计入 `dependency` 计数与主归类
—— 手动停止、条件分支正常跳过不是被测系统的问题。执行级主归类取「首个失败步骤」的类别，
其余类别保留在 `failureClasses` 计数里，不做加权排序，避免「聚合结果看不出原始失败」。

### 9.2 报告导出（M2-4）

**API**

```
GET /api/executions/:id/export?format=junit|html|json     # 单条执行
GET /api/suite-runs/:id/export?format=junit|html|json     # 一次套件执行（N 条流程）
```

| 项 | 规则 |
|---|---|
| `format` | 缺省 `json`；大小写不敏感；其余值 → `400 EXPORT_BAD_FORMAT` |
| 记录不存在 | `404 EXECUTION_NOT_FOUND` / `404 SUITE_RUN_NOT_FOUND` |
| 响应头 | `Content-Type`：`application/xml` / `text/html` / `application/json`，均 `charset=utf-8`；`Content-Disposition: attachment; filename="<ascii 兜底>"; filename*=UTF-8''<percent-encoded>` |
| 文件名 | `heibaihe-<flowName 或 suiteName>-<id 前 8 位>.<junit.xml|html|json>`；非 ASCII 字符替换为 `-`，中文原名走 `filename*` |
| 数据来源 | 与详情页同一份 `store.getExecutionDetail()` + `enrichExecutionDetail()`，再统一过 `reporting/scrub.js` |
| 执行中 | 不阻塞；导出的是「当前已落库步骤」的快照，UI 按钮旁标注 |

**格式映射**

| 格式 | 消费者 | 结构与必含 |
|---|---|---|
| JUnit XML | Jenkins / GitLab CI | 根 `<testsuites>`；每个 Flow = 一个 `<testsuite>`；每个 Node = 一个 `<testcase>`；`tests/failures/skipped/time` 与步骤逐条对齐；失败步骤 `<failure type="<failureClass>" message="<failureReason>">`，正文含请求行、响应状态与耗时、失败断言、错误文本；`skipped/waiting/pending` 输出 `<skipped message>` 且不计入 failures；套件导出额外写 `<properties>`：`suite.runId`、`suite.name`、`environment`、`flaky`、`attempts`；`<system-out>` 放执行摘要 |
| HTML | 人 | 单文件、内联 `<style>`、**无任何外链**（无 `<link>` / `<script src>` / 图片 URL / web font）；汇总卡（通过/失败/跳过/耗时/主归类）+ 失败清单 + 8 类计数 + 每步可折叠详情（请求、响应、期望、断言、错误）；全部文本经 HTML 转义 |
| JSON | 机器 / 回归 diff | `{ version: 1, kind: 'execution' \| 'suite-run', generatedAt, scrubbed, execution \| { suiteRun, executions } }`；`scrubbed` 声明本次剥离了哪些位置，便于消费者判断证据完整度 |

**S8 导出脱敏（`reporting/scrub.js`）**

| 位置 | 策略 | 理由 |
|---|---|---|
| 请求头 | 敏感键 → 值替换为 `***` | `authorization` / `cookie` 本身就是凭证容器 |
| 请求 URL query | 敏感参数名 → 值 `***`，其余保留 | 保留 `id`、`ms` 等可复现参数，报告仍可复现请求 |
| 请求体（JSON / form / 原始字符串） | 递归敏感键 → `***` | `password` / `token` / `apiKey` 提交值 |
| 响应头 | 同上（含 `set-cookie`） | 会话凭证不能随报告外发 |
| 响应体、提取变量 | **不按键名剥离**，只保留写入时已做的 env secrets 隐码 | 报告的价值在证据：`data.token` 是被测系统的输出，剥掉后结构断言无法复盘 |
| 事件流 `events[].payload` | 同一套字段级规则（`request` / `headers` / `url` / `body`） | 防止 `step_end` 事件绕过步骤脱敏 |
| `failureReason` / `error` | 不二次处理（写入时已基于 `mask(step)`） | 归类证据链与导出内容同源 |

敏感键判定（归一化后去 `-`/`_`/空格，再匹配）：精确集合
`authorization / proxy-authorization / cookie / set-cookie / password / passwd / pwd / secret / client-secret / token / access-token / refresh-token / id-token / api-key / x-api-key / session / credential / private-key`
，外加后缀规则 `password / passwd / secret / token / apikey / authorization / cookie / credential / privatekey`（覆盖 `userPassword`、`accessToken`、`clientSecret`、`x-api-key`）。

**取舍（必须写清）**：不做「整包扫 32 位随机串」的黑名单 —— 会误伤 `orderId`、`requestId`、哈希摘要，让报告失去证据价值。
S8 的验收标准因此是三条：① 环境 secrets 明文在任何格式中都不出现；② 上述敏感键的值一律 `***`；③ 导出前后步骤数、通过/失败/跳过计数与页面完全一致。

## 12. 质量门（Definition of Done）

一个 issue 算完成，必须同时满足：

1. 有对应的 `FR-*` 编号与验收条件；
2. 新增/变更的跨模块结构（DSL 字段、事件信封、导出格式、错误码）已回填 `docs/DSL.md` / `docs/EXECUTION.md`
   与本文对应小节，并声明**唯一事实源**：当前不拆包，后端 `reporting/` 是归类与导出格式的事实源，
   前端只做展示镜像（`constants/failure.ts`）；跨端格式变更必须在本文写清契约而非各端各写一份；
3. 有单测（domain 层必须；infra 层至少 happy path）；
4. `lint + test:coverage + verify` 本地全绿（根目录 `npm run ci`），CI 同序；
5. 涉及用户可见链路的改动，必须在 `backend/scripts/verify-e2e-*.mjs` 增加至少 1 条场景检查（真实 HTTP/Socket/临时库，不 mock 内核）；
6. 若涉及安全项（§8），附验证命令与输出；
7. 若涉及性能项，附改动前后数字（不写"感觉快了"）。

> 跨端共享的枚举（失败归类、状态机、事件名）只允许一处事实源：后端 `reporting/classify.js` 为准，
> 前端 `constants/failure.ts` 只做镜像展示。改动枚举时必须同步 `docs/DSL.md` / `docs/EXECUTION.md`
> 与 `verify-e2e-scenes.mjs` 的场景 9，并在 `classify.test.js` 里补「证据 → 类别」用例。
>
> 同理，S8 脱敏口径只有 `reporting/scrub.js` 一处：新增敏感字段类型时必须同步 §9.2 与场景 10
> （导出/脱敏），并保证 `export.test.js` 的「明文标记零命中」断言仍然成立。
>
> 会话恢复口径只有 `engine/scheduler.js`（快照写入 / 续跑）与 `engine/recovery.js`（重启重建）一处：
> 改动 `resume_json` 字段、`executed`/`done` 语义或 `flow_resume` 时必须同步 §5.3.1、`docs/EXECUTION.md` §7.1
> 与场景 11，并保证 `recovery.test.js` 的「已完成节点不重跑 / secret 不落快照」断言仍然成立。
