## 1. 三句话结论

1. **黑盒链路已经闭环且经过真实项目验证**：Apifox MCP 直连 → 接口列表 → 勾选绑定 → 源码扫描匹配 → 按业务分组生成流程 → 执行 → 断言匹对 → 提缺陷。这条链路是资产，不要动骨架。
2. **"白盒"目前名不副实**：它是"静态调用链 + 人工点通过"，没有运行时证据、没有覆盖率、没有自动化判定。这是与"自动化测试平台"定位之间最大的缺口，也是本次重设计的核心。
3. **工程化底座缺失**：JSON 全量重写存储、无鉴权、CORS `*`、任意目录浏览、无测试/无 lint/无 CI。这些在单机自用阶段可以忍，**做桌面端分发之前必须补**，否则装到别人机器上就是安全事故。

### 3.3 黑白盒测试模式 —— 🟡（黑盒扎实，白盒是空壳）

| 维度 | 黑盒 | 白盒 |
|---|---|---|
| 用例来源 | Apifox 契约 + 源码调用顺序 | Java 静态调用链 |
| 执行方式 | axios 真实请求，逐节点 | **人工在画布上点"通过/不通过"** |
| 判定依据 | 状态码 + JSONPath 断言 + 包含 + 耗时上限 | **人的主观判断 + 备注** |
| 运行时证据 | 请求/响应/耗时/断言明细 | 无 |
| 覆盖率 | 无 | 无 |
| 变量传递 | `extract` + `{{var}}` | 无 |
| 条件流转 | 边条件表达式（`$.code == 0 && ...`） | 静态 `if/switch` 转成边条件 |

**结论：白盒必须补的是"运行时证据"，不是"更好的画布"。** 具体路径见 `02-架构与项目结构.md` §6（JaCoCo agent per-node reset/dump）。

- ❌ 无"用例集/套件"（Suite）：23 条流程只能一条条跑，不能"选 10 条一起跑并出一份报告"。
- ❌ 无数据驱动（数据集 × 流程）。
- ❌ 无失败重试 / 无 flaky 标记。
- ❌ 无前后置脚本（现有 `action.type` 只有 `http` / `manual`）。
- 🟡 断言只能手写，没有"从契约 schema 自动生成断言/入参"。

```
                │ REST /api/*                       │ WS /socket.io  (room = exec:<id>)
┌───────────────▼───────────────────────────────────▼────────────────────────────┐
│ backend :3310  Express 4                                                        │

       │ stdio                    │ axios                   │ fs 只读
┌──────▼─────────┐    ┌───────────▼──────────┐   ┌──────────▼──────────┐
│ Apifox MCP     │    │ 被测服务（内网）      │   │ 本机前端工程目录     │
│ apifox-mcp-    │    │ 192.168.1.157/...    │   │ codePath            │
│ server(npx)    │    └──────────────────────┘   └─────────────────────┘
└────────────────┘
                                          ┌────────────────────────────┐
                                          │ java-analyzer.jar（离线）   │
                                          │ java -jar … --out flows.json│
                                          │ → 页面粘贴导入白盒流程      │
                                          └────────────────────────────┘
```

**三点观察：**
1. **执行引擎是"单进程 + 内存会话 + 逐节点同步 await"**。简单、可调试，但并发能力为 1，流程集跑不了并行。
2. **白盒分析器是进程外工具（jar）**，靠"生成 JSON → 页面粘贴"交接。这是最脆弱的一环：不可自动化、不可 CI、结果不可追溯。
3. **没有"环境"这一层**：`baseUrl` 散落在项目、流程变量、节点 URL 三处。

## 7. 与新目标的差距（一句话版）

| 你说的核心 | 现状 | 差什么 |
|---|---|---|
| Apifox 接口列表 | 拉取、绑定、生成流程全通 | 缺**契约版本与变更影响面**；缺环境层；1.7k 条性能 |
| 项目代码目录 | 前端调用点扫描 + 路径匹配 + 业务分组 | 缺**后端路由发现**、**符号级精度**、**增量扫描** |
| 黑白盒测试模式 | 黑盒闭环；白盒=人工 | 缺**白盒运行时证据（覆盖率）**、套件、数据驱动、重试 |
| 测试结果 | 三段式明细 + 实时事件 | 缺**失败归类**、**导出**、**diff**、**断点续跑** |
| 执行效果 | 单次动画 + 首页统计 | 缺**趋势**、**覆盖率热图**、**门禁/CI** |

这 5 行就是 `01-需求分析.md` 的需求来源，也是 `02-架构与项目结构.md` 里里程碑排序的依据。
