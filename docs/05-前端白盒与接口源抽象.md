# 前端白盒与接口源抽象（方向纠偏）

> 定稿日期：2026-11-10。背景：M3-1 ~ M3-4 把「白盒」实现成 **JVM 运行时行覆盖率（JaCoCo）**，
> 隐含前提是"被测代码是后端 Java 服务"。而本产品的真实输入是**前端代码目录 + API 接口契约**
> （例如输研 1.0 关联 `E:\yzkj\bSmartV3\projects\transfusion-research-web`，1737 条接口快照、161 个调用点）。
> 结果就是：对白盒投入最重的部分，对用户真正要测的对象**永远拿不到证据**。
>
> 本文重新定义白盒证据、给出不推翻既有资产的实施路径，并把「接口来源」抽象成可插拔适配层。

---

## 0. 判定：哪里跑偏、哪里没跑偏

| 能力 | 与目标「前端代码 + API 接口 → 业务实现分析 → 黑盒/白盒测试」的匹配度 | 结论 |
|---|---|---|
| 项目 = 代码目录 + 接口快照 + 流程 + 环境 | 输入端模型完全一致，且已解决「一份 Apifox 文档服务多个前端工程」 | ✅ 保留 |
| 调用点扫描 / 路径匹配 / 功能分组 / 流程生成 | 方向正确，但深度不足（只有"调用点顺序"，没有"谁调用了它"） | 🟡 升级为 W1 |
| 黑盒执行（引擎、断言、变量、环境/密钥、套件、报告、缺陷、导出、恢复） | 已闭环，占产品价值的大头 | ✅ 保留 |
| 白盒 = JaCoCo 行覆盖 | 对**前端仓库不可用**；对可加 `-javaagent` 的 Java 后端才可用 | ❌ 冻结为可选后端适配器 |
| 接口来源 | Apifox ✅、OpenAPI 文件 ✅；Postman / HAR ❌；且来源与项目模型耦合 | 🟡 抽象化 |
| 多项目管理 | 已有项目级隔离；缺跨项目对比与增量 | 🟡 归 M4 |

**偏差发生在「白盒证据的定义」，不在分层架构。** 因此修正方式是替换证据源与采集方式，
不需要重构 `engine / environments / suites / reporting / infra.store`。

## 1. 前端白盒的证据分层（W1 ~ W4）

「前端代码的白盒」回答的不是"这行执行了没有"，而是**代码 ↔ 接口的可追溯证据链**：

| 层 | 回答的问题 | 手段 | 侵入性 | 优先级 | 里程碑 |
|---|---|---|---|---|---|
| **W1 调用链还原** | 这个接口被哪些页面/操作触发？这条业务规则写在哪个函数？ | AST 静态分析（import/export 图 + 调用回溯） | 0（只读目录） | **P0** | M3'-2 |
| **W2 参数三方对比** | 代码实际传了什么 / 契约要求什么 / 真实请求发了什么，差在哪？ | AST 取参数字段集 + 契约 schema + 执行实测请求 | 0 | **P0** | M3'-3 |
| **W3 分支可达** | 接口的成功/失败/权限分支，用例覆盖到哪几条？ | 静态分支枚举 + 用例打标 | 0 | P1 | M3'-3 附带 |
| **W4 运行时覆盖率** | 做完这个业务操作，前端哪些行/分支真的跑到了？ | 插桩构建（istanbul）或 CDP 接管系统浏览器（V8） | 需前端配合一次构建 | P1 | M3'-5 |
| W5 后端 JVM 覆盖率 | 后端 Java 类/方法命中 | JaCoCo agent（**已实现**） | 需 `-javaagent` | 可选 | 冻结 |

W1 + W2 是用户要的「业务功能分析」本体，**零侵入、对输研 1.0 立刻可用**；
W4 是把"第 3 步失败时走到了哪些代码"补成运行时事实，按 2026-11-10 决定排在 W1/W2 之后。

## 2. W1 · 调用链还原（`codegraph`）

### 2.1 输出模型

```
CodeGraph
 ├─ nodes[]
 │   ├─ File        { path, kind: page|component|store|api|other, exports[] }
 │   ├─ Fn         { id, file, line, name, params[], async }          ← 复用 scanner 的 functionNameAt 口径
 │   ├─ CallSite   { id, file, line, fnId, method, rawPath, argsKeys[] } ← 现有 scanner.js 的产物
 │   └─ Endpoint   { interfaceId, method, path }                      ← 项目接口快照
 ├─ edges[]
 │   ├─ imports    { from: File, to: File, binding, localName }
 │   ├─ calls      { caller: Fn, callee: Fn }
 │   └─ triggers   { caller: Fn, callSite: CallSite }
 └─ chains[]  Endpoint ← CallSite ← Fn ← …… ← EntryFn(page)   多条、带置信度
```

### 2.2 实现口径（不做的事写清楚）

- **解析器**：新增依赖 `@babel/parser`（`plugins: ['typescript','jsx','decorators-legacy','classProperties']`），
  自写约 120 行递归 walker，**不引入 `@babel/traverse`**（体积与 scope 生成对本用途是负债）。
- **`.vue` 处理**：只提取 `<script>` / `<script setup>` 块交给 parser（正则定位块边界，
  与 scanner 现有的行号偏移处理一致）；**不引入 `@vue/compiler-sfc`** —— 那会把前端工具链拖进后端与桌面 sidecar。
  `template` 里的 `@click="doX"` 用轻量正则提取绑定名，作为 `calls` 边的补充来源（置信度 medium）。
- **入口判定**：路由表优先（`vue-router` 的 `component: () => import('...')` 与 `children`），
  退化为「`views/**` 或 `pages/**` 下的 SFC 默认导出」视为入口。
- **回溯深度**：默认 6 层、单接口最多 20 条链路、总图节点上限 20000，超限截断并在结果里标 `truncated`
  （沿用 scanner 的"上限可配 + 明确标注"风格，绝不静默截断）。
- **动态写法兜底**：`import()` 变量、`obj[name](...)`、mixin 继承 → 标 `confidence:'low'`，
  进「人工关联」列表，复用现有 `POST /api/projects/:id/mapping` 的交互与 `matchSource` 字段。
- **与既有扫描器的关系**：`projects/scanner.js` **保留**为 CallSite 提取器（W0）；`codegraph` 消费它的
  `calls[]` 再补 import/calls/triggers 三类边。不重写、不并行两套文件遍历。

### 2.3 验收（AC-W1）

- W1-1：输研 1.0 的 161 个调用点中，**≥ 90%** 能给出至少一条「入口文件 → … → api 函数」链路。
- W1-2：随机抽 20 条链路人工核对，正确率 **≥ 95%**；错的那条必须显示为"低置信度待确认"而不是"高置信度"。
- W1-3：`api/trsCheckBill.js#getPageList` 能从接口反查所有调用它的页面组件，点击可跳到 `文件:行`。
- W1-4：全量扫描（约 2000 文件）< 60 s；二次扫描走增量 < 10 s；扫描在 worker 线程跑，不阻塞执行引擎。
- W1-5：孤儿接口清单（绑定了快照但代码里没有任何调用点）与"无入口调用点"分开统计，
  两者都不得计入"已覆盖"（延续"不伪装"原则）。

> **口径修订（2026-11-10，实机校准后）**：W1-1 的分母改为「有工程内调用方的调用点」。
> 输研 1.0 实测 61/93 个已匹配调用点在工程内无任何调用方（死代码或值传递），
> 它们不可能有入口链路；全局 43% 与可归因口径 100% 必须同时展示，见 §2.4.1。

### 2.4 实施记录（M3'-2 已落地，与 2.1~2.3 同为 SSOT）

落地位置：

```
backend/src/codegraph/
  parse.js     # .vue 取 <script>/<script setup>（保留 lineOffset）、template 绑定/组件标签、@babel/parser 封装
  walker.js    # 自写 DFS walker + nameOf/paramNames（不引 @babel/traverse）
  extract.js   # 单文件事实：imports / functions / calls(含 paramKeys) / exports / default
  resolve.js   # 说明符 → 工程内文件（相对路径、@/ ~/、省略扩展名、目录 index；node_modules 一律 null）
  build.js     # 图构建：节点/三类边/入口/触发/回溯/统计
  store.js     # 旁路存储 data/codegraph/<projectId>.json
  index.js     # 签名、链路装饰、按接口/调用点查询、调用方、涉及文件、摘要
backend/src/projects/codegraphService.js   # 项目级 build/status/chains/gaps/callers/read
```

对 2.1/2.2 的**补充口径**（实现中发现必须写清的）：

1. **组件使用边 `component`**（父页面 → 子组件）：模板里的 `<PayerDialog />` / `<payer-dialog>` 不带调用语法，
   但没有它，弹窗/抽屉子组件里的接口调用**永远回溯不到入口**，只能显示"无入口链路"。
   判定不看标签黑名单，而是「该文件是否 import 了同名绑定」——`<el-button>`（工程外）自动排除。
   置信度 `medium`，计入调用方关系（`edges.components`）。
2. **全量图旁路存储**：`nodes/edges/chains` 不进 SQLite（几 MB 会拖死项目详情接口），
   落 `data/codegraph/<projectId>.json`；库里只存摘要（`project.codegraph` + `scan_summary_json.codegraph`）。
   摘要带 `signature = sha1(root|scannedAt|callCount|calls.id+matchedId+matchSource|interfaceIds)`，
   扫描/手工关联/接口集变化即 `stale`。
3. **状态机**：`missing`（无扫描）/ `stale`（`not-built` 或 `scan-changed`）/ `fresh`。
   查询接口一律返回 `state`，未构建时给 `notice` 文案——**不允许用空数组冒充"没有调用方"**。
4. **断链降级**：`reason=no-entry` / `depth-limit` 的链路强制 `confidence=low`；
   `orphanInterfaces`（文档有、代码无调用点）与 `noEntryCalls`（有调用点、回溯不到入口）分开统计，
   `interfacesWithoutEntry` 单独列出。
5. **截断显式**：`truncated` + `truncatedReasons ∈ {node-budget, chain-limit, call-site-limit}` +
   `skippedFiles[]`。`call-site-limit` 来自 scanner 的 `calls.slice(0, 1200)`：
   图只能覆盖这 1200 个调用点，必须标明而不是装作全量。
6. **参数口径**（供 M3'-3 W2 的 A 侧）：`extractParamKeys` 把实参拆成
   `query`（`params`/`query`）/ `body`（`data`/`body`）/ `payload`（其余业务键）；
   `url/path/method/headers/timeout/responseType/baseURL` 是传输配置，不计入业务参数。
7. **`resolveOptions` 防静默**：`{...DEFAULTS, ...{maxDepth: undefined}}` 会让
   `results.length < undefined` 恒假 —— 图建成功但一条链路都没有。显式 `null/undefined` 一律回落默认值。
8. **作用域边分两类**（`edges.scopes`，`via='module-scope' | 'closure'`）：
   `<script setup>` 顶层函数由模板事件/生命周期直接使用，回调（`ids.forEach((id) => api(id))`）由调用方执行，
   源码里都**没有调用语法**。缺这两类边，回溯会断在普通函数上（输研 1.0 首轮实测入口链路率 0%）。
   它们只是「可达性」证据，**不进 `callersOf()` 的调用方列表**，也不参与 `callerCount` 统计。
9. **入口三来源**：路由表 `router` → `views|pages/**` 兜底 `views-fallback` → `App.vue` 根组件 `app-root`。
   `views/*/dialog|components` 归 `component`（弹窗不是入口，否则接口链路会「回溯到自己」）；
   `index.vue` 用父目录名当入口名，避免一屏全是 `index`。
   路由页面的 `export default defineComponent({...})` 与 `<module>` 视为同一入口（`entryByFn` 双映射）。
10. **别名解析三类兜底**（`resolve.js`）：`@/` 先试 `src/` 再回落到工程根（兼容「根即源码根」的工程）；
    以工程自身包名作别名（`@transfusion-research-web/api/x.js`）时，**只有去掉 scope 后的路径真实存在**才解析，
    因此 `@commonlib/*`、`@element-plus/*` 等外部包不会被误认成工程内文件；解析不了的工程内说明符进 `unresolvedImports`（裸包名不算断链）。
11. **触发点匹配容错**：模板串 `` `${BASE}/x` `` 的 AST 路径是 `/{}/x`，与 scanner 的 `/x` 不同；
    先去掉起始占位段再比，仍不同才用 `matchScore ≥ 70 && 行差 ≤ 3` 兜底。`matchedBy` 仍如实标 `line`/`file`。
12. **模板 prop 传组件**：`:assay-component="AssayTabs"` 这类「组件以 prop 传入通用弹窗」也要建 `component` 边
    （`via='component-prop'`），只认大写开头标识符，避免把 `:config="dialogConfig"` 当成组件。
13. **排序**：链路按「有入口 → 置信度高 → 跳数少」排（`bestFirst`），UI 首条与断言都取这条；
    `noEntryCalls[]` 带 `callerCount`，为 0 时明示「工程内无调用方」，而不是含糊的「无入口」。

接口（`routes/projects.js`）：

| 方法与路径 | 语义 |
| --- | --- |
| `POST /api/projects/:id/codegraph` | 构建/重建；复用 `project.scan.calls`（与流程生成同口径） |
| `GET /api/projects/:id/codegraph` | 状态 + 摘要（`state/reason/summary/signature`） |

#### 2.4.1 实机校准（输研 1.0，250 文件 / 6451 函数 / 161 调用点）

首版在真实工程上跑出「93 个已匹配调用点，0 条入口链路」。逐层排查后修掉 6 类真实缺陷——
它们都不是测试能覆盖的写法差异，因此全部补了回归用例：

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| ① | 入口链路率 0% | 只有 `module-scope` 边，回调函数没有可达性 | 加 `closure` 边（父函数 → 声明在其中的函数），`scopeEdgeCount=4174 / closureEdgeCount=2027` |
| ② | `@/…` 的 116 条 import 全断 | 工程没有 `src/`，代码就在根目录 | `aliasBases` 先试 `src/`、再回落工程根 |
| ③ | `@transfusion-research-web/…` 311 条 import 全断 | 单体仓库用自身包名当别名 | 新增 `scopedFallback`，仅当「去 scope 后路径真实存在」才解析 |
| ④ | 触发点 `matchedBy=file`、链路断在 module | 模板串 `` `${BASE}/x` `` 与 `/x` 路径不等 | 先剥起始占位段，再用 `matchScore ≥ 70 && 行差 ≤ 3` 兜底 |
| ⑤ | 页面明明走到入口却判 `no-entry` | 路由页入口 fn 是 `<default>`，回溯落在 `<module>` | `entryByFn` 同时映射 module fn |
| ⑥ | 弹窗里的接口回溯不到页面 | `<AssayStartDialog :assay-component="AssayTabs" />` 以 prop 传组件 | 解析 `:prop="Component"` 建 `component` 边（`via='component-prop'`） |

修复前后（同一工程、同一份 scanner 产物）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `callsWithEntry` | 0 | 70 |
| `callChainRateAmongCallable` | 0% | **100%**（70/70） |
| `callChainRate`（原始分母） | 0% | 43%（70/161） |
| `endpointChainRate` | 0% | **76%**（67/88） |
| `componentEdgeCount` | 115 | 187 |
| 构建耗时 | 450 ms | 479 ms |
| `unresolvedImportCount` | — | 82（全部为 `@commonlib/*` 等工程外包，非工程内断链） |

**为什么不是 90%**：93 个已匹配调用点中 **61 个在工程内没有任何调用方**（全仓 grep 逐一复核：
58 个是从未被引用的导出函数，3 个只作为值传给通用函数如 `fetchHistorySuggestions(keyword, getApplicantOptions, cb)`）。
这类调用点不存在「入口 → api」的链路，把它们的失败算进算法正确率会得出误导性结论。
因此对外同时给两个数：`callChainRate`（含孤儿调用点，43%）与 `callChainRateAmongCallable`（100%），
`noEntryCalls[]` 用 `callerCount=0` 明示属于哪一类；**23 个断链一条都没有隐藏**。

**性能（W1-4 抽样）**：合成 2101 文件 / 11102 函数 / 13000 调用边，构建 **530 ms**，
`truncatedReasons=['chain-limit']`（链路数触顶，显式标注），图 JSON 9.7 MB。
`< 60 s` 已满足，增量扫描与 worker 线程化仍未做。

#### 2.4.2 项目页调用链面板（W1-3 UI 闭环）

**状态机文案**（`graphStateView`，四种状态可区分，未构建不允许查询）：

| 后端 `state/reason` | 标签 | 提示 | 能否查询 |
|---|---|---|---|
| `missing` | 未扫描（红） | 先完成「② 扫描代码调用流程」，附跳转按钮 | 否 |
| `stale / not-built` | 未构建（黄） | 「点构建调用链才会产出；在此之前**不显示 0 条链路**」 | 否 |
| `stale / scan-changed` | 需重建（黄） | 下面显示的是上一次的图，重建后才算证据 | 是（旧图可看） |
| `fresh` | 可用（绿） | — | 是 |

**双分母统计**（`graphStatRows`）：`有入口调用点 = 70/70`，副标题同时写
`可归因 100% · 全局 43%`；`接口入口率 = 76%（67/88）`。两个数不合成一个，
因为合成后无论取哪个都会误导（合并 → 低估算法；只取可归因 → 掩盖 61 个死代码调用点）。

**断链四组 + 孤儿**（`gapSections` / `noEntryRows` / `orphanRows`），互不合并：

| 分组 | 内容 | 措辞约束 |
|---|---|---|
| 无入口调用点 | `noEntryCalls[]`，带 `callerCount` | `callerCount=0` 才显示「工程内无调用方（死代码/未被引用）」，否则「有 N 个调用方但回溯不到入口」 |
| 未解析调用 | 动态写法 `obj[name](…)`、变量 import | 「需人工关联」，不写成失败 |
| 未解析 import | 工程内路径找不到（裸包名不计入） | 与断链分开，避免把 `@commonlib/*` 当工程问题 |
| 解析失败文件 | 单个坏文件 | 「不会拖垮整张图，但必须让人看见」 |
| 孤儿接口 | 文档有、代码无任何调用点 | 与「无入口调用点」明确区分 |

链路卡片：置信度 `low` 用 **warning 而非 danger**（`confidenceTone`）——低级置信度是「待人工确认」，
不是错误；断链文案统一为「断链 · 低置信度待关联」+ `brokenReasonText`，**任何分支都不出现「无调用方」**。

**源码行窗口**（`readSource` + `GET /codegraph/source`）：

- 白名单：`file` 必须命中 `graph.nodes.files` 的 id，图外文件一律 400（`文件不在本次调用链图内`）；
- 二次校验：`path.resolve(root, file)` 必须仍在 `project.codePath` 内，防 `../` 越界；
- 上限：单文件 ≤ 2 MB、`radius ≤ 80`（默认 12），只返回 `[line-radius, line+radius]` 行窗口；
- 返回 `{ state, file, absolutePath, line, startLine, endLine, totalLines, truncated, lines[{nr,text}] }`，
  前端抽屉高亮目标行并支持「复制绝对位置」。**不提供任意路径读取**，看源码不等于文件浏览器。

**验证证据**：

- 前端单测 `frontend/test/codegraph-utils.test.mjs` **7 例**（状态机 4 态、双分母、无分母显示 `—`、
  端点筛选/排序、断链文案、`callerCount` 归类、分组与截断原因），前端总 **19 例全绿**；
- 后端 `test/codegraph-service.test.js` 增至 **8 例**，新增源码定位用例
  （行窗口 2–6、行号收敛、`radius` 上限、`../../secret.txt` 与 `/etc/passwd` 均拒绝、未构建时返回 `stale` 而非「文件不存在」）；
- 场景 14 扩为 **14.1~14.10**：14.8 行窗口 `window=2-6` 命中 `/trsCheckBill/page`；
  14.9 图外路径 `status=400`；`npm run verify:scenes` **105 项检查全 PASS**；

## 3. W2 · 参数三方对比

三个来源做交集/差集，任一来源缺失时**该维度显示"未知"**，不得当作"无差异"：

| 来源 | 取法 | 缺失时 |
|---|---|---|
| **A 代码传参** | CallSite 的第二/三实参：对象字面量键集、`qs.stringify({...})`、`{ params, data }` 解构 | `无代码证据` |
| **B 契约定义** | 接口快照的 `pathParams / queryParams / bodySample`（Apifox/OpenAPI 都有） | `无契约` |
| **C 实测请求** | 执行时 `step.request` 的真实 URL query 与 body（已有掩码链路） | `未执行` |

差异分类 → 建议动作：

| 差异 | 含义 | 动作 |
|---|---|---|
| B 必填 ∧ ¬A | 代码漏传 | **直接生成缺陷草稿**（带 `文件:行` + 契约位置） |
| A ∧ ¬B | 文档漂移或多余参数 | 生成"契约待更新"待办，不判缺陷 |
| B 可选 ∧ ¬A ∧ ¬C | 参数未覆盖 | 生成用例草稿（补一个节点 + 一条断言） |
| A ∧ ¬C | 运行时被覆盖/丢弃（拦截器改写、序列化丢失） | 判为高价值发现，进 W4 协同采集验证 |

UI：接口详情抽屉显示三列对照 + 差异徽标；项目「③ 业务功能闭环」上方给出差异汇总条；
「差异 → 一键生成用例」复用现有流程 DSL，不新增用例模型（建模铁律 1 不变）。

**验收（AC-W2）**：在测试桩上人为构造 4 类差异，四类全部检出且各自给出可跳转定位；
来源缺失时显示对应"未知"徽标，绝不显示"一致"。

## 4. W4 · 运行时前端覆盖率（无重型浏览器）

2026-11-10 决定：**不下载 Chromium**（不引 playwright/puppeteer 的浏览器产物）。两条路线，A 先做：

### 4.1 路线 A · 插桩构建 + 采集端点（默认）

1. 黑百盒提供一段可选的 Vite 配置片段（`vite-plugin-istanbul`，用户自己工程里加，**黑百盒不改用户代码**）；
2. 构建/dev 后页面运行时把 `window.__coverage__` 在约定时机 POST 到
   `POST /api/coverage/ingest`（body：`{ coverageId, payload }`）；
3. 服务端按 istanbul 的 `statementMap / branchMap / fnMap` 归一化成既有 `Coverage` 结构。

### 4.2 路线 B · CDP 接管系统浏览器（兜底）

Windows 自带 Edge（Chromium 内核），macOS 有 Safari/Chrome：
`msedge.exe --remote-debugging-port=9222` → 黑百盒用 `ws` + CDP
（`Profiler.enable` / `startPreciseCoverage` / `takePreciseCoverage`）采集，
V8 字节区间经 **sourcemap** 映射回源文件行。**只依赖 `ws`，不依赖任何浏览器分发。**

### 4.3 关键语义：采集必须与"业务操作"绑定

黑盒节点只发 HTTP，**不会执行前端 JS**。因此"第 3 步命中了哪些前端代码行"必须由
**协同采集窗口（watch session）**成立，而不是假装自动发生：

```
节点声明 coverage.watch = true
  → 执行到该节点时状态置 waiting（复用现有人工确认交互，界面明确"请在页面上完成此操作"）
  → 窗口开始：collector.reset()
  → 用户在真实前端页面操作，浏览器持续上报
  → 窗口结束：collector.dump() → 归因到该节点 coverageId
```

- 复用既有表与语义：`coverage.mode` 扩展取值 `watch`（该列是 TEXT 无 CHECK，**不需要 ALTER**）；
  `source` 扩展 `istanbul | v8` —— 需要同步放宽 `environments/service.js` 的
  `const COVERAGE_SOURCES = ['jacoco']` 为 `['jacoco','istanbul','v8','lcov']`；
- 三态语义原封不动：`analyzed` / `captured + pending` / `unavailable`，
  **窗口内没有任何上报 = `unavailable`，不允许显示 0% 或"通过"**（延续 AC-3.2.7）；
- 断言方言扩展：JVM 用 `pkg.Class#method`，前端用 `src/api/trsCheckBill.js#getPageList`
  （路径 + `#` + 导出函数名）。`parseCoverageTarget` 增加方言判定，判定逻辑（在报告里且 covered>0 / 不在或 covered===0）不变。

### 4.4 验收（AC-W4）

- W4-1：插桩构建的示例前端，一次 watch 能拿到 ≥ 1 个 api 文件的行级覆盖，面板可跳源码。
- W4-2：同一节点连续两次 watch，命中集合差异可解释（reset 生效，不累积）——与 AC-3.2.2 同口径。
- W4-3：用户不开页面操作（窗口内 0 上报）→ 节点显示「无运行时证据」，断言按 `script` 归类判失败，**不静默通过**。
- W4-4：`/api/coverage/ingest` 必须鉴权 + 校验 `coverageId` 归属会话 + 限制体积（≤ 4 MB）与频率，
  上报内容不进导出包（S8 同口径）。

## 5. 接口来源抽象（InterfaceSource）

按 2026-11-10 决定：**先把 Apifox 落成第一个标准适配器，后续平台平滑插入**。
形态取「**统一中间模型 + 适配器注册表 + 工厂**」，即抽象工厂的落地写法；
不引入复杂的桥接层级，因为变化维度只有一个（来源），另一个维度（项目/快照/匹配/生成）不该感知来源。

### 5.1 目标目录

```
backend/src/sources/
  registry.js        # name → adapter；describe() 能力声明；工厂按 kind + config 实例化
  contract.js        # InterfaceSource 契约 + InterfaceSnapshot 中间模型（唯一落库形态）
  apifox/index.js    # 收编现有 apifox/service.js + mcpClient.js
  openapi/index.js   # 收编现有 importers/openapi.js（已支持文件导入）
  postman/index.js   # M3'-1 后续：Collection v2.1
  har/index.js       # 后续：HAR 1.2（浏览器直接导，带真实参数值）
```

### 5.2 契约

```js
interface InterfaceSource {
  kind: 'apifox' | 'openapi' | 'postman' | 'har',
  label: string,
  describe(): {
    kind, label,
    capabilities: { folders, examples, auth, incremental, recordedValues },
    configFields: [{ key, label, required, secret }],   // 前端表单由此渲染，不再硬编码 Apifox 字段
  },
  fetch(config, ctx?): Promise<{
    interfaces: InterfaceSnapshot[],   // 与今天 projects 用的快照结构一致
    meta: { kind, fetchedAt, sourceHash, interfaceCount, fromCache, warnings[] },
    // 兼容字段（apifox 路径原样透传，SRC-1 靠复用而不是重写保证）
    title?, version?, baseUrl?, count?, fetchedAt?, fromCache?
  }>,
  // 可选能力：不存在时上层按「不支持」降级，绝不假装成功
  snapshot?(ids, config): Promise<InterfaceSnapshot[]>,  // 勾选接口 → 完整快照（绑定项目）
  cached?(config): { title, version, baseUrl, fetchedAt, interfaces } | null,
  test?(config): Promise<{ ok, title, version, baseUrl, interfaceCount }>,
}
```

实现口径（M3'-1 已落地，与本节同为 SSOT）：

- **唯一落库形态仍是 `InterfaceSnapshot`**；差异只存在于 `fetch` 内部，
  `projects/service.js` 的勾选/匹配/生成流程不感知来源。
- **注册表**：`registry.create(kind)` 是唯一工厂；未注册/空 kind 抛 `SOURCE_UNKNOWN`，
  重复注册抛 `SOURCE_DUPLICATE`（不静默覆盖）。`GET /api/sources` 直接返回 `describe()` 数组。
- **通用入口**：
  `GET /api/sources`、`GET /api/sources/:kind`、
  `POST /api/sources/:kind/fetch`、`POST /api/sources/:kind/test`。
  项目主流程仍走 `/api/projects/:id/*`，新增来源只注册适配器即可（SRC-2）。
- **错误码**（`SourceError.code`，路由映射 400；`SOURCE_UPSTREAM` 映射 502）：

  | code | 含义 | 典型场景 |
  | --- | --- | --- |
  | `SOURCE_UNKNOWN` | 来源类型未注册 | 拼错 kind / 尚未实现 postman |
  | `SOURCE_NOT_CONFIGURED` | 缺少必要配置 | 没填项目 ID 且无缓存 / 没传 spec |
  | `SOURCE_BAD_DOCUMENT` | 文档不是合法 OpenAPI | JSON 解析失败、缺 `paths` |
  | `SOURCE_EMPTY` | 文档合法但 0 条接口 | 导出内容选错 |
  | `SOURCE_BAD_SNAPSHOT` | 快照字段残缺 | 适配器投影 bug |
  | `SOURCE_DUPLICATE_INTERFACE` | 快照里接口 ID 重复 | 文档本身重复 |
  | `SOURCE_UPSTREAM` | 远端/令牌/网络失败 | MCP 连不上、令牌过期 |

- **Apifox 适配器**复用 `apifox/service.js` 的传输与缓存（MCP + `data/apifox/oas-cache.json`），
  缓存/降级分支与重构前逐行对齐：未配置→缓存优先；有项目无令牌→同项目缓存；
  强制刷新才走 MCP；连接标识回写全局配置，**令牌只在显式传入时回写**。
- **OpenAPI 适配器**接受对象或 JSON 字符串；`snapshot()`/`cached()` 优先用
  `project.source.config.spec`（项目自带文档），否则回退到本进程最近一次 `fetch`，
  避免「A 项目刚拉的文档被 B 项目的 available 读到」。
- 项目配置字段演进：`project.apifox { projectId, siteId, branchId, apiBaseUrl }`
  → `project.source { kind, config }`，迁移期**双写兼容**（老字段读时归一化，新写入走 `source`；
  非 apifox 来源会清空 apifox 镜像，避免列表页显示错的项目 ID）。
- **来源凭证一律走 `environment_secrets`（AES-256-GCM）**，`project.source.config` 只存非敏感标识；
  延续 S8：令牌不进导出包、不进执行记录。
- 多来源并存（二期）：同一项目允许绑多个来源，快照带 `sourceRef`；冲突按「最新抓取 + 人工指定权威源」，
  差异本身即"契约漂移"报告，是增值项而不是负担。

### 5.3 验收（AC-SRC）

- SRC-1：把 Apifox 改造为适配器后，`GET /api/projects/:id/available`、`POST /api/projects/:id/pull`
  的响应字段与行为**零变化**（回归护栏：既有 13 个功能域场景 + 深场景全绿）。
- SRC-2：新增 Postman 适配器时，`projects/service.js`、`routes/*`、前端项目页的改动合计 **≤ 20 行**
  （只加注册表项与 `configFields` 渲染，不改主流程）——这条是抽象是否成立**唯一的硬指标**。
- SRC-3：来源不可用（令牌过期、文件解析失败）必须返回稳定错误码与可读原因，
  不得回退成"拉到 0 条接口"的空成功。

## 10. 一句话总结

> 产品主线回到「**读前端代码 + 读接口契约 → 还原业务实现 → 黑盒执行验证 → 白盒证据（链路/参数/覆盖）→ 缺陷闭环**」；
