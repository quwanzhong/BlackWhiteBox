## 1. 产品定位与非目标

### 1.1 一句话定位

**把"接口契约"和"项目代码"缝合成可执行的业务流程，用一套流程同时跑黑盒与白盒，并给出可复现、可导出、可进 CI 的测试结果。**

### 1.2 与常见工具的区别（决定我们做什么、不做什么）

| 工具类型 | 代表 | 它们强在哪 | 黑百盒的差异 |
|---|---|---|---|
| 接口调试 | Postman / Apifox | 单接口调试、契约管理 | 我们**不重复做接口调试**，直接消费 Apifox 契约 |
| 接口自动化 | Postman Runner / Pytest | 脚本化断言 | 我们用**画布 + DSL**，把业务链路可视化，非技术同学也能改流程 |
| UI 自动化 | Cypress / Playwright | 浏览器真操作 | 现阶段**不做 UI 自动化**，只做接口级 + 代码级 |
| 代码覆盖率 | JaCoCo / c8 | 跑完给一份总覆盖率 | 我们做**按节点归因的覆盖率**：能回答"第 3 步失败时，它走到了哪些行" |

**核心差异点（护城河）：一个节点 = 一次请求 + 一段断言 + 一份代码覆盖证据。** 现有产品里很少有把这三者绑在同一条时间线上的。

### 1.3 非目标（本期明确不做，写下来是为了防止范围蔓延）

| 非目标 | 理由 |
|---|---|
| 通用 API 调试器（类似 Postman 的任意请求构造） | Apifox 已经做了，重复投入无收益 |
| UI/端到端浏览器自动化 | 执行模型是"节点=HTTP+代码证据"，UI 需要完全独立的驱动层 |
| 性能压测（并发/阶梯加压/RPS 曲线） | 与"一次执行一条链路"的模型冲突，属另一个产品 |
| 测试用例管理系统（需求-用例-缺陷的完整 ALM） | 只做"缺陷"这一个出口，不做需求管理与测试计划审批流 |
| 多租户 SaaS / 权限体系（RBAC 到按钮级） | 先做单机/小团队；只做"本机访问令牌"这一层最小安全 |
| 自研 Java 全量语义分析（对标 Spoon/JavaParser 全能力） | 保留现有 `com.sun.source` 方案，精度不足处用运行时证据补 |

## 2. 角色与关键旅程

### 2.1 角色

| 角色 | 谁 | 主要诉求 | 使用频率 |
|---|---|---|---|
| **R1 测试工程师**（主角色） | QA | 把接口变成业务链路、跑、看结果、提缺陷 | 每天 |
| **R2 开发工程师** | 后端/前端 | 看自己的接口被哪些流程覆盖、失败是不是自己改坏的 | 每周 |
| **R3 技术负责人** | TL/QA Lead | 看趋势、看覆盖率、决定能不能发版 | 每迭代 |

> 现版本只有一个隐含角色（"会用画布的人"）。R2/R3 的诉求在现有产品里完全没有承载：没有"我的接口"视图，没有趋势，没有门禁。

### 2.2 三条关键旅程（Journey，用于反推功能优先级）

#### J1 · 新项目接入（R1，首次，目标 ≤ 30 分钟）

```
新建项目 → 选前端代码目录 → 连 Apifox（项目ID + 令牌）→ 拉接口(1737)
   → 勾选本次要测的接口(比如 12 条) → 扫描源码匹配调用点
   → 自动按业务分组 → 生成 3 条黑盒流程 → 逐条微调断言
   → 跑通第一条 → 保存为"冒烟套件"
```

**现状卡点**：1737 条接口列表全量渲染（D9）；无"套件"，跑完只能一条条点；断言全手写。
**验收**：从新建到第一条流程跑通 ≤ 30 分钟；接口列表 1737 条下滚动不掉帧。

#### J2 · 日常回归（R1，每天，目标 ≤ 3 分钟看到结论）

```
打开首页 → 选"冒烟套件" → 一键执行(12 条流程)
   → 实时看画布发光 → 3 条失败 → 看失败归类(超时/断言/状态码)
   → 对失败项一键重跑 → 确认为真 bug → 提缺陷(带请求/响应/断言/覆盖证据)
```

**现状卡点**：无套件（D12 串行也是瓶颈）；无失败归类（D7）；重跑要重开页面。
**验收**：12 条流程一条命令跑完并出汇总；失败原因 90% 能被自动归到 8 类之一，不需要人读原始响应。

#### J3 · 白盒定位（R2，出问题当天，目标 ≤ 10 分钟）

```
R2 收到缺陷 → 打开该次执行 → 点开失败节点
   → 看到"本次执行命中了 OrderService.java 的 42/58 行"
   → 看到未覆盖的 16 行正是异常分支 → 判断"测试没覆盖到，不是代码错"
   → 或反过来：命中了但返回错 → 定位到具体行 → 修
```

**现状卡点**：这是**完全不存在**的能力（D2）。白盒目前是人工点"通过"。
**验收**：能对单个节点给出 `coveredLines / totalLines / 未覆盖行号列表`，误差可解释。

## 3. 领域模型

### 3.1 模型图（概念级）

```
Workspace（本机工作区，单例）
 └─ Project（项目 = 一个前端工程 + 一个 Apifox 项目 + 一个被测服务）
     ├─ CodeSource（代码目录 + 扫描结果 ScanResult）
     │    ├─ CallSite（文件:行, 函数, HTTP 方法, 原始路径）
     │    └─ SymbolIndex（类/方法/行号，用于白盒定位）
     ├─ EndpointSet（Apifox 接口快照，1737 条）
     │    └─ Endpoint（id, method, path, folder, schema, version）
     ├─ Environment（dev/test/prod：baseUrl + 变量 + 密钥引用）   ← 新增
     ├─ Suite（套件 = 有序的 Flow 列表 + 执行策略）               ← 新增
     └─ Flow（流程 = 用例，唯一执行单元）
         ├─ Node（节点：action=http|manual|script；expected；extract）
         │    └─ Coverage（该节点的行覆盖证据）                   ← 新增
         ├─ Edge（边：condition 表达式）
         └─ Execution（一次执行）
             ├─ Step（节点执行记录 + Check[] + Coverage）
             ├─ Defect（可选：由失败步骤提升而来）
             └─ RunSummary（passed/failed/skipped/duration）
```

### 3.2 实体定义（只写新增与变更，存量见 `docs/DSL.md`）

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `Environment` | `id, name, baseUrl, variables{}, secrets{}` | `secrets` 只存引用名，值存本地密钥库，**不进导出包** |
| `Suite` | `id, projectId, name, flowIds[], strategy{concurrency,retry,failFast}, schedule?` | 解决"23 条流程只能一条条跑" |
| `Endpoint.version` | `hash, capturedAt, diff?` | 契约快照，用于"接口改了哪条用例受影响"（D6） |
| `Coverage` | `nodeId, source, type(jacoco\|v8\|lcov), files[{path, covered[], missed[], total}]` | 白盒运行时证据（D2） |
| `FailureClass` | 枚举 8 类 | `network / timeout / status / schema / assertion / dependency / script / manual_reject` |

### 3.3 三条建模铁律

1. **Flow 是唯一用例模型。** 不引入并行的 `TestCase`。套件只是 Flow 的集合，报告只是 Execution 的聚合。
2. **Node 是唯一的执行与归因单元。** 请求、断言、覆盖证据、缺陷都必须挂在 Node/Step 上，不允许有"游离于节点之外的结果"。
3. **环境与密钥必须外置。** 任何 `baseUrl`、token、账号不得硬编码在 Flow 里（现状三处散落，D8）。

**验收（AC-3）**
- AC-3.2.2：同一流程连跑两次，第二次执行第 3 节点时，覆盖率只包含第 3 节点触发的代码行，不累积前两节点的命中（证明 per-node reset 生效）。
- AC-3.2.4：给定一个失败节点，能在 UI 上看到 `covered 42 / total 58` 与未覆盖行号列表，点击行号跳到对应源码行（只读）。
- AC-3.2.5：若节点断言"应命中 `OrderService.create`"，实际未命中，判定为 **failed** 且失败归类为 `assertion`，而不是静默通过。
  - 反向断言同样成立：声明"不应命中 `PaymentClient.refund`"而实际命中 → failed + `assertion`。
  - 证据不可用（未采集 / 未配 `classfiles` / 分析失败 / 人工节点声明断言）→ 也判 failed，但归类为 `script`（配置/环境问题），并给出可读原因；**不允许把"没跑分析"当通过**。
  - 目标写错（格式非法、类/方法在报告里不存在）→ mustHit 视为未命中（`assertion`），非法规格单独报 `coverage_evidence`。
- AC-3.2.7：覆盖率降级必须可区分且不误导——
  - **未配置** agent：执行结果白盒字段为 `null`（JSON 中无 `coverage` 键 / `count=0`），UI 显示"无运行时证据"徽标；
  - **配置了但不可达**：每个节点一行 `status='unavailable'` + 稳定错误码（如 `COVERAGE_AGENT_UNREACHABLE`），节点结论仍由自身断言决定；
  - 两种情况下都**不得**显示 `0% 覆盖`，也不得因此把节点改判为通过或失败。
- **AC-3.2.8（W1）**：161 调用点的前端仓库中，≥ 90% 调用点能给出至少一条入口链路；随机 20 条人工核对正确率 ≥ 95%；
  断链必须显示为低置信度待关联，**不得显示为"无调用方"**。
- **AC-3.2.9（W2）**：桩上人为构造的四类参数差异全部检出，每条差异给出可跳转的 `文件:行` 与契约位置；
  任一来源缺失时该维度显示"未知"，**不得显示"一致"**。
- **AC-3.2.11（W4）**：watch 窗口内 0 上报 → 节点判 `unavailable` + `script` 归类失败；两次 watch 结果差异可解释（reset 生效）；
  采集端点必须鉴权、限体积（≤ 4 MB）、上报内容不进导出包（S8）。
- **AC-3.2.12（来源抽象）**：Apifox 改适配器后 `available/pull` 响应零行为变化；
  **新增 Postman 适配器时 `projects/service.js`、`routes/*`、前端项目页改动合计 ≤ 20 行**（抽象是否成立的硬指标）；
  来源不可用返回稳定错误码，不得回退成"拉到 0 条接口"的空成功。

### 5.2 安全（桌面化前置，全部 P0）

| 需求 | 说明 |

### 5.3 可复现性

- 每次 Execution 必须能"凭记录完整重放"：环境快照（baseUrl 不含密钥）、Flow 版本、变量初值、随机种子。
- 报告里必须写明"用了哪个环境的哪个版本"，否则三个月后无法解释一次失败。

### 5.4 可维护性

- `backend/src` 与 `frontend/src` 分层依赖单向（见 `02` §4）。
- 引擎与扫描器必须有单测，覆盖率 ≥ 70%；CI 全绿才可合并（D5）。
- 单个 `.vue` 文件 ≤ 300 行；超了必须拆组件（D9）。

### 5.5 跨端

- 核心逻辑（引擎/断言/存储）必须与 UI 解耦，能以 Node 进程形式被 Tauri/Electron 壳复用。
- 桌面端只允许增加"壳能力"（文件选择、系统托盘、自动更新），不允许分叉业务逻辑。
